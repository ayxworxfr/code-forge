# 企业级 Admin 脚手架设计方案（Node 全栈）

## 一、项目定位

### 1.1 目标

构建一套 **拿来即用** 的企业级 Admin 脚手架，用于快速启动管理系统项目（中后台），并满足长期演进需求。

核心目标：

- 新项目 30 分钟内可启动并完成首个业务模块开发
- 默认具备上线必需的工程能力（认证、权限、日志、测试、CI/CD、监控）
- 保证统一规范，降低团队协作与维护成本

### 1.2 当前阶段边界

- 首期聚焦通用 Admin 场景（认证、权限、用户、日志、配置等）
- 商城、支付、物流等垂直能力作为后续可选业务模块扩展
- 代码生成、低代码能力不纳入首期范围，但保留后续接入接口

---

## 二、设计原则

### 2.1 产品原则

- 开箱即用：生成后可直接登录、鉴权、建模块、发布
- 默认最佳实践：工程质量门禁默认开启
- 渐进式复杂度：小团队可轻量使用，大团队可启用高级治理能力

### 2.2 架构原则

- 前后端分层清晰，领域边界清晰
- 业务优先组合，避免过度抽象
- 插件化扩展，避免核心代码膨胀
- 全链路可观测，问题可定位可回滚

### 2.3 交付原则

- 每个版本必须可创建项目、可运行、可发布
- 破坏性升级必须提供迁移脚本与回滚方案

---

## 三、总体方案

## 方案 A：模板仓库复制（不推荐）

- 思路：维护一个固定模板仓库，项目通过 `git clone` 使用
- 优点：实现最快
- 缺点：升级困难、分叉严重、组织治理能力弱

## 方案 B：CLI + 固定模板（可用）

- 思路：`create-admin-app` 从内置模板生成项目
- 优点：统一入口，体验好
- 缺点：扩展能力有限，长期会臃肿

## 方案 C：CLI + 模块插件 + 标准模板（推荐）

- 思路：核心模板稳定，业务能力以插件模块叠加
- 优点：标准化与扩展性平衡，最适合长期演进
- 缺点：初期设计成本较高

### 选型结论

采用 **方案 C**：以稳定模板为核心，以模块插件实现扩展。

## 四、技术架构

### 4.1 技术栈（默认）

- 前端：React + TypeScript + Vite + Ant Design + Zustand + React Router
- 后端：NestJS + TypeScript + Prisma + PostgreSQL
- 缓存：Redis（可选启用）
- 认证：JWT（Access + Refresh）+ RBAC
- 文档：OpenAPI/Swagger
- 任务编排：pnpm workspace + Turbo（可选）

### 4.2 架构视图

```text
Browser(Admin UI)
      │
      ▼
Web App(React)
      │ HTTP/JSON
      ▼
API Gateway(NestJS Controller Layer)
      │
      ├── Auth Module
      ├── User & Role Module
      ├── Menu & Permission Module
      ├── Audit Log Module
      ├── File Module
      ├── Dictionary Module
      └── System Config Module
      │
      ├── PostgreSQL (主数据)
      └── Redis (会话/缓存，可选)
```

### 4.3 分层规范

- Interface 层：Controller、DTO、参数校验
- Application 层：用例编排、事务边界
- Domain 层：业务规则、领域对象
- Infrastructure 层：ORM、外部服务、缓存、消息

## 六、内置业务能力（MVP 必须具备）

### 6.1 认证与授权

- 用户登录/退出
- Access Token + Refresh Token
- RBAC（用户-角色-权限点）
- 路由级与按钮级权限控制

### 6.2 系统管理

- 用户管理
- 角色管理
- 菜单管理
- 权限点管理
- 部门/组织管理（可选）

### 6.3 平台能力

- 操作审计日志（谁在何时做了什么）
- 字典管理（状态枚举、业务枚举）
- 系统配置（可热更新的键值配置）
- 文件上传（本地/S3 兼容对象存储）

### 6.4 开发友好能力

- 统一异常处理与错误码
- 统一分页、排序、筛选协议
- 统一响应结构
- API 自动文档与类型共享

### 6.5 国际化能力（i18n）

- 前端内置多语言框架（默认 `zh-CN` / `en-US`），支持运行时切换语言
- 菜单、权限点、字典项支持国际化键，避免文案硬编码
- 后端错误码与消息分离，支持按语言返回可本地化文案
- 统一处理时区、日期时间、数字与货币格式，避免跨区域展示不一致
- 提供 i18n 资源校验脚本（缺失键、无用键、命名冲突）并接入 CI

- `standard`：常用企业后台（含日志、字典、文件）
- `enterprise`：增强版（含缓存、监控、灰度、审计策略）

每个业务模块按统一契约接入：

- 后端：module + controller + service + repository + migration + test
- 前端：route + page + api + store + permission points
- 脚手架负责将模块挂载到系统菜单与权限体系

# 通用全栈脚手架设计方案

## 一、设计目标

### 1.1 背景

现有项目可以作为经验来源，但不应被视为最终形态。新脚手架的目标不是“能跑起来”，而是做到：

- 可持续迭代：3 年后依旧易维护
- 团队级协作：多人并行开发成本低
- 企业级质量：安全、测试、发布、可观测性内建
- 业务友好：新项目初始化从天级降到分钟级

### 1.2 核心目标

构建一套 **Node 全栈通用脚手架平台**，满足以下要求：

1. 一次命令完成项目初始化（前端 + 后端 + 基础设施）
2. 支持多技术栈组合（可插拔，不强耦合）
3. 默认即最佳实践（Lint/Test/CI/Security/Release 预置）
4. 提供企业级扩展能力（插件、模板市场、组织规范）

### 1.3 非目标

- 首期不建设低代码平台能力，后续可按组织需求评估接入
- 首期聚焦工程底座能力，业务逻辑生成能力作为可选扩展方向
- 首期控制技术栈范围，优先保证质量与可维护性，再逐步扩展

---

## 二、设计原则

### 2.1 产品原则

- 默认可生产：生成即具备上线最小条件
- 约定优于配置：80% 场景开箱即用
- 渐进式复杂度：小项目轻量，大项目可逐步启用高级能力
- 人机协同：兼容 AI 代码助手但不依赖 AI 才能用

### 2.2 技术原则

- Monorepo 优先，边界清晰
- 插件优先于硬编码
- 架构先于模板，模板先于脚本
- 所有能力必须可测试、可观测、可回滚

---

## 三、方案对比与选型

## 方案 A：模板仓库直拷贝

- 核心思路：维护多个模板仓库，按场景复制
- 优点：实现快，学习成本低
- 缺点：模板分叉严重，升级困难，组织成本高
- 适用：单团队、短期项目
- 结论：不作为长期主方案

## 方案 B：单体 CLI + 固定模板

- 核心思路：一个 CLI 提供初始化能力，模板内置
- 优点：一致性好，体验统一
- 缺点：技术栈扩展困难，版本演进容易臃肿
- 适用：技术栈基本不变的团队
- 结论：可作为过渡形态

## 方案 C（推荐）：核心引擎 + 插件生态 + 模板工厂

- 核心思路：脚手架拆分为 Core、Plugin、Template 三层
- 优点：扩展性、治理能力、长期维护性最强
- 缺点：初期建设成本高
- 适用：希望长期沉淀工程能力的团队/组织
- 结论：推荐采用

### 选型结论

采用 **方案 C**，并分阶段落地，避免一次性过度建设。

## 四、总体架构设计

### 4.1 架构分层

```text
┌────────────────────────────────────────────────────────────┐
│                    Scaffold CLI (入口层)                  │
│  create / add / remove / upgrade / doctor / release       │
└───────────────────────┬────────────────────────────────────┘
                        │
┌───────────────────────▼────────────────────────────────────┐
│                     Core Engine (核心层)                  │
│  配置解析 | 生命周期 | 依赖图 | 任务调度 | 回滚 | 日志       │
└───────────────┬───────────────────────┬────────────────────┘
                │                       │
┌───────────────▼──────────────┐ ┌──────▼────────────────────┐
│     Plugin Runtime (插件层)   │ │   Template Factory(模板层) │
│  前端插件 | 后端插件 | 运维插件 │ │  变量渲染 | AST 改写 | 合并策略│
└───────────────┬──────────────┘ └──────────┬─────────────────┘
                │                           │
┌───────────────▼───────────────────────────▼─────────────────┐
│                    Generated Workspace                      │
│ apps/web | apps/server | packages/shared | infra | tools   │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 关键能力

- 生命周期钩子：`init`、`beforeRender`、`afterRender`、`postInstall`
- 幂等执行：重复运行 `add plugin` 不破坏已有代码
- 冲突处理：文件冲突提供 merge 策略（自动/交互/拒绝）
- 任务编排：基于 DAG 执行插件任务，支持并行与失败回滚

## 七、插件体系设计（核心）

### 7.1 插件模型

```ts
export interface ScaffoldPlugin {
  name: string;
  version: string;
  requires?: string[];
  conflicts?: string[];
  apply(ctx: PluginContext): Promise<void>;
}
```

### 7.2 插件分类

- App 插件：`web-react`、`server-nest`
- Domain 插件：`auth-jwt`、`audit-log`、`i18n`
- Infra 插件：`docker`、`ci-github`、`observability`
- Quality 插件：`eslint-enterprise`、`test-e2e`

### 7.3 生命周期

1. `validate`：校验依赖冲突
2. `plan`：生成变更计划
3. `render`：渲染模板与改写配置
4. `install`：安装依赖
5. `verify`：执行 smoke checks
6. `finalize`：输出变更报告

### 7.4 版本策略

- 核心引擎与插件分离版本
- 插件必须声明与 Core 的兼容范围
- `upgrade` 命令支持“预检 -> 迁移 -> 回归”

---

## 八、模板引擎设计

### 8.1 模板形态

- 文本模板：用于代码与配置文件生成
- AST 模板：用于 `package.json`、`tsconfig.json` 等结构化改写
- 组合模板：支持模板片段复用

### 8.2 渲染变量

- 基础变量：项目名、包管理器、Node 版本、仓库地址
- 架构变量：前后端框架、ORM、测试框架
- 组织变量：命名规范、代码所有者、CI 策略

### 8.3 冲突策略

- `overwrite`：完全覆盖
- `merge`：结构化合并
- `append`：追加内容
- `manual`：人工确认（生成补丁文件）

## 十、质量保障与工程化

### 10.1 必备质量门禁

- pre-commit：lint + typecheck
- pre-push：unit tests
- CI：lint + typecheck + unit + build
- PR 模板：变更说明、风险说明、回滚方案

### 10.2 测试策略

- Core：单元测试覆盖核心引擎

## 十一、安全与合规

### 11.1 安全基线

- 默认启用依赖漏洞扫描（`pnpm audit` + SCA 工具）
- 环境变量白名单与 schema 校验
- 生产配置默认关闭调试信息
- 模板执行隔离，不允许任意执行系统命令

### 11.2 供应链安全

- 插件签名与来源校验（组织私仓优先）
- 锁定插件版本，禁止未审计自动升级
- 发布流程加入 SBOM（软件物料清单）

## 十二、发布与升级策略

### 12.1 发布节奏

- 每月小版本（功能增强）
- 每季度大版本（架构变更）
- 紧急补丁版本（安全和阻断问题）

### 12.2 升级机制

- `scaffold upgrade --check`：仅检测不修改
- `scaffold upgrade --apply`：自动迁移
- `scaffold upgrade --rollback`：基于快照回滚

### 12.3 兼容策略

- LTS 支持两个大版本
- 破坏性变更必须提供迁移脚本与迁移文档

## 十三、实施路线图（分阶段）

### Phase 1（4 周）：MVP 可用

- Core 引擎最小能力（create/add/doctor）
- 两个核心插件：`web-react-vite`、`server-nest`
- 工程基线插件：`eslint`、`ci-github`、`docker`
- 输出 3 套预设：`minimal`、`standard`、`enterprise`

### Phase 2（4-6 周）：专业化

- 插件依赖图与冲突检测
- 升级系统（check/apply/rollback）
- 模板 AST 合并能力
- 完整 E2E 样例项目矩阵

### Phase 3（6-8 周）：平台化

- 插件市场（组织内）
- 配置可视化与策略中心
- 项目健康扫描与治理报告
- 多团队规范下发与审计

## 十五、风险与应对

| 风险 | 描述 | 应对 |
|------|------|------|
| 过度设计 | 一次性做太全导致延期 | 严格按 Phase 交付，先 MVP |
| 插件质量不齐 | 社区插件不可控 | 组织认证插件白名单 |
| 升级破坏项目 | 自动迁移误改业务 | Dry-run + 快照回滚 + 契约测试 |
| 技术栈膨胀 | 维护成本失控 | 可选栈准入机制与淘汰机制 |

## 十六、与现有项目的关系（借鉴但不绑定）

现有项目可沉淀的经验：

- 模板驱动思路可复用
- 前后端 TypeScript 一体化路径可复用
- 配置、历史、可视化管理经验可复用

需要升级的方向：

- 从“单项目实现”升级到“平台型脚手架”
- 从“功能可用”升级到“工程治理可持续”
- 从“本地工具视角”升级到“组织级研发基础设施”

---

## 十七、推荐结论

- 推荐采用：**核心引擎 + 插件体系 + 模板工厂** 三层架构
- 推荐策略：**先 MVP，后专业化，再平台化**
- 关键落点：先把“可复制的工程质量”做成默认能力，再做高级功能

该方案的本质不是再造一个模板项目，而是构建团队可长期复用、可治理、可演进的研发底座。
